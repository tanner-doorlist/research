## Problem
No single reference existed explaining how the knowledge scribe system fits together: how ChromaDB is spawned and kept alive, how the Python MCP server connects to it, how the Electron app interacts with it indirectly, and how raw developer notes eventually become study cards. The system has multiple moving parts across three separate processes and two separate data stores.

## Initial Observations
- ChromaDB is not embedded — it runs as a standalone HTTP server, which means connection lifecycle matters
- The Electron app never touches ChromaDB directly, which is non-obvious
- Study cards and ChromaDB embeddings look related but are actually independent stores
- The log-to-card pipeline has three discrete manual steps with no automatic sync between them

## Approach

1. Trace ChromaDB lifecycle: Electron spawns `chroma run` on launch via `startChroma()`, guarded by a heartbeat check at `localhost:8000/api/v2/heartbeat`. If already running, spawn is skipped. Process is killed on `before-quit`. Data persists on disk at `knowledge-mcp/chroma_db/` (SQLite + HNSW), so restarts are safe.
2. Trace MCP server → ChromaDB: Python server uses `chromadb.HttpClient`. `get_collection()` is called fresh on every tool invocation (not cached) to avoid stale UUID failures after a ChromaDB restart. Logs are embedded with `text-embedding-3-small` (1536 dims) and stored with metadata; search embeds the query and uses cosine similarity, then fetches the full markdown from disk via the filename in metadata.
3. Trace Electron app → ChromaDB: The app spawns `python3 cli.py search` as a subprocess for search queries. The chain is renderer → IPC → main.js → Python CLI → ChromaDB HTTP. The app never calls ChromaDB directly.
4. Trace log-to-card pipeline: Three manual steps — (a) `log_knowledge()` formats notes with Claude and writes markdown + indexes in ChromaDB; (b) `generate_study_cards()` reads unprocessed markdown from `problem-logs/`, calls Claude, appends Q&A and concept cards to TSV files, marks files processed in `.processed_logs.json`; (c) Electron reads TSV files directly. ChromaDB is not involved in card generation or display.

## Key Insights
- **`get_collection()` must never be cached**: a cached collection object holds a UUID that becomes stale if ChromaDB restarts; calling it fresh on every invocation is the intentional defensive pattern.
- **Two stores, intentionally decoupled**: ChromaDB holds embeddings + first 1000 chars for semantic search; TSV files hold full Claude-generated study cards. Deleting one does not affect the other — this is by design, not an oversight.
- **ChromaDB serves two roles only**: dedup checking on ingest and semantic search in the knowledge browser. Everything else — cards, study sessions — runs entirely on markdown and TSV files.
- **The Electron app is a thin shell over subprocesses**: it delegates all knowledge operations to the Python CLI, keeping the ChromaDB dependency entirely in Python land.

## Solution
The system has three runtime processes and two persistent stores:

**Processes:**
1. `chroma run` HTTP server (spawned by Electron, persists to `chroma_db/`)
2. Python MCP server (`server.py`) — handles `log_knowledge` and `search_knowledge` via HTTP client to ChromaDB
3. Electron app (`main.js`) — spawns ChromaDB, delegates search to Python CLI subprocess

**Pipeline (manual, three steps):**
1. `log_knowledge()` → Claude formats notes → markdown written to `problem-logs/` → embedded and indexed in ChromaDB
2. `generate_study_cards()` → reads unprocessed markdown → Claude extracts Q&A/concepts → appended to `qa_cards.tsv` / `concept_cards.tsv` → marked processed in `.processed_logs.json`
3. Electron reads TSV files directly for study card display — ChromaDB not involved

**Two independent stores:**
- `chroma_db/`: embeddings, metadata, first 1000 chars — powers semantic search
- `study-cards/*.tsv`: full study cards — powers card review UI

## Pitfalls / What to Watch For
- **Assuming study cards come from ChromaDB**: they don't — they come from TSV files generated by a separate manual step. ChromaDB and the card pipeline share the markdown source but are otherwise decoupled.
- **Caching the ChromaDB collection object**: safe until ChromaDB restarts, then silently fails with a stale UUID error. Always call `get_collection()` fresh.
- **Assuming the pipeline is automatic**: none of the three steps trigger each other. Logging a note does not generate cards; generating cards does not require ChromaDB to be healthy.
- **Deleting `chroma_db/` thinking it resets everything**: it only breaks semantic search. Markdown files, TSV cards, and `.processed_logs.json` are all unaffected.
- **Assuming Electron talks to ChromaDB directly**: it only ever spawns it. All queries go through the Python CLI subprocess chain.

## Study Prompts
Q: Why does the Python MCP server call `get_collection()` on every tool invocation instead of caching it at startup?
A: A cached collection object holds the collection's UUID. If ChromaDB restarts, that UUID becomes stale and subsequent calls fail. Calling `get_collection()` fresh each time ensures a valid handle regardless of ChromaDB restarts.

Q: If `chroma_db/` is deleted, what breaks and what is unaffected?
A: Semantic search breaks (no index), and dedup checking on new logs breaks. Study cards (TSV files), markdown problem logs, and `.processed_logs.json` are all unaffected — the two stores are intentionally decoupled.

Q: What is the full call chain when the Electron renderer triggers a knowledge search?
A: Renderer → IPC message → `main.js` IPC handler → `spawn('python3', [cliPath, 'search', ...])` → `cli.py` → `chromadb.HttpClient` → ChromaDB HTTP server → results returned back through stdout → IPC → renderer.

Q: What triggers study card generation from a new knowledge log?
A: Nothing automatic. A developer must manually invoke the `generate_study_cards()` MCP tool, which runs `generate_study_cards.py --new-only` to process unprocessed markdown files and append cards to the TSV files.
